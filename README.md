Newman-ийг `sudo npm install -g newman`-ээр суулгасан. Тестлэх API бол лабын `server.js` (цэвэр Node, сан хэрэггүй): `node server.js` → `http://localhost:3000`.

## Даалгавар 1: Анхны хүсэлт ба oracle

`lab05-collection.json` доторх «Д1» хавтас: `PUT /students/B231234567` (идэвхтэй, CS201 үзсэн) → `PUT /courses/CS313` (урьдач нь CS201) → `POST /registrations`. POST дээр хоёр `pm.test` oracle байгаа: статус `201` ба `result = "OK"`. URL бүр `{{baseUrl}}` collection variable (`http://localhost:3000`) ашиглана.

## Даалгавар 2: Тест дизайн

### Алхам 1 — Бие даан тестлэгдэх функц

`POST /registrations` — `{studentID, courseID}` авч, оюутныг хичээлд бүртгэнэ. Оюутан ба хичээлийн төлөвийг `PUT /students/:id`, `PUT /courses/:id` setup хүсэлтүүдээр урьдчилан тавина.

### Алхам 2–3 — Сонголтууд ба төлөөлөх утгууд

| Сонголт (параметр / орчин) | Анги | Төлөөлөх утга |
|---|---|---|
| **A. studentID-гийн хүчинтэй байдал** | A1 идэвхтэй | `PUT /students/X {"status":"active"}` |
| | A2 идэвхгүй | `{"status":"inactive"}` |
| | A3 байхгүй | хэзээ ч PUT хийгээгүй ID (`B000000000`) |
| **B. Оюутны үзсэн хичээлүүд** | B1 урьдачийг хангана | `coursesTaken: ["CS201"]` |
| | B2 хангахгүй | `coursesTaken: []` эсвэл өөр хичээл |
| **C. courseID-гийн хүчинтэй байдал** | C1 байгаа | `PUT /courses/CS313` хийсэн |
| | C2 байхгүй | PUT хийгээгүй ID (`CS999`) |
| **D. Хичээлийн урьдач нөхцөл** | D1 бүгдийг үзсэн | prereq `["CS201"]`, үзсэн `["CS201"]` |
| | D2 огт үзээгүй | prereq `["CS201"]`, үзсэн `[]` |
| | D3 зарим нь | prereq `["CS201","CS202"]`, үзсэн `["CS201"]` |
| | D4 урьдачгүй (хязгаар) | prereq `[]` |
| **E. Хүсэлтийн формат** | E1 зөв JSON, хоёр талбар бүтэн | `{"studentID":…,"courseID":…}` |
| | E2 талбар дутуу | `{"studentID":…}` |
| | E3 буруу JSON | `{"studentID":` |

**Боломжгүй / утгагүй хослолууд:**
- A3 (оюутан байхгүй) × B/D — байхгүй оюутанд «үзсэн хичээл» гэж байхгүй, тиймээс урьдач нөхцөлийн ангиуд хамаарахгүй.
- C2 (хичээл байхгүй) × D — байхгүй хичээлд урьдач нөхцөл гэж байхгүй.
- E2/E3 × бусад бүх анги — формат буруу бол сервер оюутан, хичээлийг огт шалгахгүй.

### Алхам 4 — Спецификациуд

| # | Ангиуд | Тохиолдол | Хүлээгдэх статус | Хүлээгдэх `result` |
|---|---|---|---|---|
| S1 | A1 B1 C1 D1 E1 | Happy path: идэвхтэй, CS201 үзсэн оюутан CS313-д | 201 | `OK` (+ `registrationID` тоо) |
| S2 | A3 C1 E1 | Оюутан байхгүй | 200 | `ERROR_NO_STUDENT` |
| S3 | A2 B1 C1 D1 E1 | Оюутан идэвхгүй (бусад нь зөв) | 200 | `ERROR_INACTIVE_STUDENT` |
| S4 | A1 C2 E1 | Хичээл байхгүй | 200 | `ERROR_NO_COURSE` |
| S5 | A1 B2 C1 D2 E1 | Урьдач нөхцөлийг огт үзээгүй | 200 | `ERROR_PREREQUISITES`, `missing=["CS201"]` |
| S6 | A1 B2 C1 D3 E1 | Урьдачийн зарим нь дутуу | 200 | `ERROR_PREREQUISITES`, `missing=["CS202"]` |
| S7 | A2 C2 E1 | Давхар алдаа: идэвхгүй **ба** хичээл байхгүй | 200 | `ERROR_INACTIVE_STUDENT` (тестээр тогтоосон) |
| S8 | A3 C2 E1 | Давхар алдаа: оюутан **ба** хичээл хоёулаа байхгүй | 200 | `ERROR_NO_STUDENT` (тестээр тогтоосон) |
| S9 | A1 C1 D4 E1, `coursesTaken: []` | Хязгаар: урьдачгүй хичээл + хоосон coursesTaken | 201 | `OK` |
| S10 | E2 | Хязгаар: `courseID` талбар дутуу | 400 | `ERROR_BAD_REQUEST` |
| S11 | E3 | Хязгаар: буруу JSON бие | 400 | `ERROR_BAD_JSON` |

Стратеги (Лекц 5): happy path 1 (S1), алдааны анги бүрд 1 (S2–S5), давхар алдаа 2 (S7, S8), хязгаар (S6, S9–S11). Нийт **11 спецификаци**.

Давхар алдааны дараалал зааварт бичигдээгүй байсан. S7 ба S8-ын тестээр сервер эхлээд **оюутныг** (байгаа эсэх → идэвхтэй эсэх), дараа нь **хичээлийг** (байгаа эсэх → урьдач нөхцөл) шалгадаг болохыг тогтоосон.

## Даалгавар 3: Collection

`lab05-collection.json` — спецификаци бүр (S1–S11) тусдаа хавтас:

- **Бие даасан байдал:** хавтас бүр өөрийн ID-тай оюутан, хичээлийг (`S3_STU`, `S3_CS313` г.м.) өөрийн `PUT` setup-аар үүсгэнэ. Ингэснээр нэг тестийн өгөгдөл нөгөөд нөлөөлөхгүй, ямар ч дарааллаар, хэд ч удаа ажиллуулж болно. «Байхгүй» ангиудад (S2, S4, S7, S8) хэзээ ч PUT хийгдээгүй ID ашигласан.
- **Oracle-ууд:** POST бүрд статус кодын болон `result` утгын `pm.test` байгаа. S1/S9 дээр `registrationID`-ийн **яг утгыг биш, тоо эсэхийг** шалгана (сервер in-memory тул ID хуримтлагддаг). S5/S6 дээр `missing` массивыг нэмж шалгана. Setup PUT бүрд мөн `200` oracle бий.
- Нийт **11 тест (хавтас), 24 хүсэлт, 39 assertion**.

## Даалгавар 4: Newman-аар автоматжуулах

Гурван ажиллуулалт. Exit code-ийг `| tee`-ийн дараа `${PIPESTATUS[0]}`-оор авсан (bash):

```bash
newman run lab05-collection.json 2>&1 | tee results/newman-pass.txt
echo "exit=${PIPESTATUS[0]}"
```

| Ажиллуулалт | Collection | requests (executed / failed) | assertions (executed / failed) | Exit code |
|---|---|---|---|---|
| PASS | `lab05-collection.json` | 24 / 0 | **39 / 0** | **0** |
| FAIL | `lab05-collection-fail.json` | 24 / 0 | 39 / **1** | **1** |
| DOWN (сервер унтраасан) | `lab05-collection.json` | 24 / **24** | 39 / **39** | **1** |

- **PASS** (`results/newman-pass.txt`): 11 тест, 39 assertion бүгд амжилттай.
- **FAIL** (`results/newman-fail.txt`): `lab05-collection-fail.json` бол үндсэн collection-ийн тусдаа хуулбар. Ганц өөрчлөлт нь S1-ийн статусын oracle-ыг `201`-ийн оронд `200` болгосон явдал: `expected response to have status code 200 but got 201`. Newman 1 assertion унахад exit code 1 буцаадаг. CI pipeline энэ кодыг харж build-ийг зогсооно (quality gate). Үндсэн `lab05-collection.json` зөв хэвээрээ.
- **DOWN** (`results/newman-down.txt`): серверийг унтраагаад үндсэн collection-ийг ажиллуулсан. Хүсэлт бүр `connect ECONNREFUSED 127.0.0.1:3000` алдаа өгсөн, 24 хүсэлт ба 39 assertion бүгд унасан, exit code **1**.

**Интерфейсийн алдаа ба oracle-ийн алдааны ялгаа:** FAIL-д сервер хариу өгсөн боловч хариу нь бидний хүлээлттэй зөрсөн (oracle-ийн алдаа, функц эсвэл тестэд асуудал байна), харин DOWN-д хариу огт ирээгүй, учир нь сервертэй холбогдож чадаагүй (интерфейс/орчны алдаа, функцийн зөв бурууг энэ үед огт шалгаагүй).

`lab05-public-api.json` — `GET https://jsonplaceholder.typicode.com/users` хүсэлтэд 3 oracle: статус `200`, хариу нь массив, эхний хэрэглэгчийн нэр `Leanne Graham`. Гаралт: `results/newman-public.txt`, **1 хүсэлт, 3 assertion, 0 failed, exit 0**. Үндсэн collection-ийн 39 assertion-д үүнийг оруулаагүй, тусдаа collection хэлбэрээр хадгалсан.

Харьцуулалт: GET-only API-д setup хэрэггүй тул тест бичихэд маш хялбар, гэхдээ өгөгдлийг нь бид удирдаж чадахгүй учраас «Leanne Graham» гэх мэт утга гаднаас өөрчлөгдвөл тест унах, мөн алдааны ангиудыг (идэвхгүй, байхгүй г.м.) зориуд үүсгэж шалгах боломжгүй.

## Дүгнэлт

Дизайны 5 алхмаас хамгийн их бодол шаардсан нь 2–3-р алхам буюу сонголтуудыг ялгаж, анги бүрд төлөөлөх утга сонгох хэсэг байлаа. Ялангуяа «урьдач нөхцөл» гэдэг нэг сонголт мэт боловч оюутны үзсэн хичээл ба хичээлийн шаардлага гэсэн хоёр өгөгдлөөс хамаардаг тул «бүгд / огт / зарим» гэж задлахад бодох хэрэгтэй болсон. Хослолуудыг гаргахад хэд хэдэн боломжгүй хослол таарсан: байхгүй оюутанд «үзсэн хичээл» гэж байхгүй, байхгүй хичээлд урьдач нөхцөл гэж байхгүй, мөн JSON буруу бол сервер бусад бүх зүйлийг огт шалгахгүй. Тиймээс бүх хослолыг тестлэх биш, лекцийн стратегиар happy path, алдааны анги бүрд нэг, давхар алдаа, хязгаарын тохиолдол гэж 11 спецификаци сонгосон. Зааварт давхар алдааны үед аль нь буцахыг бичээгүй байсан тул S7, S8 тестээр сервер эхлээд оюутныг, дараа нь хичээлийг шалгадгийг тогтоосон. 39 assertion бүгд тэнцсэн тул тодорхойлолтоос зөрсөн согог олдоогүй. Гэхдээ кодыг уншихад нэг оюутан нэг хичээлд давхар бүртгүүлэхийг хориглосон шалгалт байхгүй байсан нь бодит системд согог болох магадлалтай, тодорхойлолтод ч энэ тохиолдлыг дурдаагүй. Тест бүрд тусдаа ID ашигласнаар тестүүд бие даасан болж, серверийг дахин асаахгүйгээр хэдэн ч удаа ажиллуулж болдог болсон. FAIL ба DOWN ажиллуулалтаас Newman алдаа гарвал exit code 1 буцаадаг тул CI-д quality gate болгон шууд ашиглаж болохыг харсан.
